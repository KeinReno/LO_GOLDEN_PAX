## Цепочка задач

### T4.1. Расширить `PlayerOrder` в `types.ts`

```typescript
export interface PlayerOrder {
  // ...существующие поля...
  category?: "instant" | "pending" | "eta"; // default "eta" для обратной совместимости
  startedAt?: number;      // turn или timestamp
  baseDuration?: number;   // в игровых часах
  modifiers?: { label: string; mult?: number; flat?: number; source: string }[];
  resolvesAt?: number;
  progress?: number;       // 0..1, для accumulating (исследования)
  ratePerTurn?: number;
}
```

### T4.2. Формулы ETA

- **Перелёт флота:** `baseDuration = distance(systemA, systemB) / fleetSpeed`. Дистанция — уже есть в
  координатах систем на карте (`src/state/types.ts` `StarSystem` координаты); скорость — характеристика
  флота/кораблей (`ships.json`, если поля скорости ещё нет — добавь минимально, не переусложняя).
- **Стройка:** `baseDuration = buildHours` из `buildings.json`/`ships.json`/`units.json`. **Если поля
  `buildHours` сейчас нет ни у одной записи** — добавь его контентно (разумные плейсхолдер-значения по
  тиру: T1≈6ч, T3≈24ч, T6≈72ч, T10≈240ч — не итоговый баланс, заглушка для цепочки).
- **Исследование:** accumulating, не fixed-ETA — `progress += ratePerTurn` каждый тик, `ratePerTurn` зависит
  от лабораторий/населения (переиспользуй существующий research-контур, если есть в `techActions.mjs`).

Ресурсы на стройку/полёт списываются **в момент старта Order**, не в момент завершения (см. спек §2) — если
сейчас списание происходит иначе, поправь.

### T4.3. `resolveDueOrders()` в `processTurn.mjs`

Новый шаг тика: проходит по `world.orders` (или где хранятся активные), у которых `category !== "instant"` и
`resolvesAt <= now`, применяет эффект (флот прибыл → сменить положение/владельца; стройка готова → добавить
юнит/здание) и переводит в `resolved`. Вызывать после экономического тика, до финального снапшота — сверься
с текущим порядком шагов в `processTurn.mjs` и вставь логично, не в конец списком.

### T4.4. AP как параллельность, не как клики

Расширь `resolveEmpireApMax` — AP тратится при **создании** Order (списывается сразу), освобождается при
`resolved`/`cancelled`. Это не "сколько действий в день", а "сколько Order можно держать одновременно
активными". Если текущая реализация трактует AP иначе — приведи к этому смыслу, задокументируй изменение
поведения в summary (это может повлиять на существующий UI индикатор AP).

### T4.5. Разметить существующие intents по категориям

В `content/core/intents.json` — пройтись по всем существующим intent'ам, проставить `category`. Смена
стойки/налога/закона/объявление войны → `instant`. Предложения (союз/сделка/торговля) → `pending`. Всё
процессное (стройка/полёт/исследование/осада/разведка) → `eta`.

### T4.6. `Proposal` — не дублировать diploOffers

Прочитай `server/diploOffers.mjs` внимательно. Если он уже реализует `status: pending/accepted/rejected` без
ETA для дипломатических предложений — не создавай параллельный `Proposal`-тип, а обобщи существующий паттерн
на прочие "ожидающие реакции" интенты (сделки/торговые предложения), если такие есть за пределами дипломатии.

### T4.7. UI: минимальная панель очереди

Список активных Order фракции, отсортированных по `resolvesAt`, формат "База → модификаторы → итог" (см.
спек §2 пример). Не обязательно новый файл — можно расширить существующую подходящую панель во
`viewer`/`editors`, если такая уже есть под похожую задачу (проверь `IntentsInbox.tsx`).

### T4.8. Округление ETA до ходов

В UI показывать ETA округлённым до целых ходов ("Готово: через 2 хода (≈40ч)"), не до минут — раз ход = сутки
(см. спек §2, конец).

### T4.9. Миграция и тесты

`normalizeWorld.mjs` — старые Order без `category`/`resolvesAt` получают дефолт `category: "eta"`,
`resolvesAt: null` (трактуется как "уже готово" или "ждёт ручной обработки" — выбери консистентно со старой
логикой, не потеряй существующие незавершённые заказы в сейвах). `npm run smoke`, `npm run smoke:tick`.

## DoD

- Флот с назначенным перелётом реально прибывает через рассчитанное число часов, не мгновенно.
- Стройка занимает `buildHours`, ресурсы списаны на старте, юнит появляется по `resolvesAt`.
- AP уменьшается при создании Order и восстанавливается при завершении.
- Панель очереди показывает активные Order с ETA в формате база→модификаторы→итог.
- `npm run smoke`, `npm run smoke:tick` проходят, старые сейвы грузятся.
