## Цепочка задач

### T1.1. Двойное начисление metal/supply из категорий B/D/E

`economyTick.mjs:738` кредитует `currency.materia`/`currency.energia`/`currency.bios` из `categoryNet`, затем
`:763-783` считает `bridgeMetal = max(0, materiaNet) + legacyGross.metal` / аналогично `bridgeSupply`, и
`:836`/`:857` кредитует `currency.metal`/`currency.supply` этими значениями **в том же тике** — то есть одна
единица производства B/D/E оплачивает две раздельные тратимые казны разом. Подтверждается контентом:
`buildings.json:154-159` (`building.factory`) ценится одновременно в `currency.metal` и `currency.materia` и
`currency.industria`.

**Если B1 ещё не запущен:** не чини здесь — впиши этот пункт в скоуп B1 (он и так переводит сток на именные
ресурсы в этой же области кода, отдельный патч будет затёрт). **Если B1 уже выполнен:** проверь, кредитуется
ли всё ещё `metal`/`supply` из `categoryNet` параллельно с именным стоком анкор-ресурса — если да, убери
дублирующий кредит, оставь один источник истины на единицу производства.

### T1.2. Арифметика урона не сохраняет пул повреждений

`combatResolve.mjs:579-586`:

```js
const absorb = Math.max(1, (g.armor||0)*0.15 + (g.shields||0)*0.1);
const effectiveDmg = dmg / Math.max(0.5, absorb / 10);   // клампится снизу
const inflicted = Math.min(hpPool, effectiveDmg);
dmg -= inflicted * (absorb / 10);                         // НЕ клампится
```

Перевод урона в HP использует `Math.max(0.5, absorb/10)`, списание из бюджета — тот же `absorb/10` без
нижнего порога. Для `absorb ≤ 5` (слабая броня — ополчение, гарнизоны, лёгкие легионы) это завышает
`effectiveDmg` до 5× относительно того, что реально списывается с бюджета атакующего. Почини: применяй один
и тот же клампнутый делитель в обеих строчках (`Math.max(0.5, absorb / 10)` в обеих формулах), чтобы один
и тот же `absorb` не давал разный курс на вход/выход пула.

### T1.3. Асимметричный кап модификатора `research`

`modifierStack.mjs:99-105` — `DEFAULT_MODIFIER_CAPS.research = {min:0.5, max:1.0}` (дублируется в
`content/core/rules.json → modifierCaps.research.max: 1`). Единственный канал, чей верхний кап не пропускает
штрафы: любой `research_cost_mult > 1` молча превращается в no-op через `clampChannelMult` (`:107-115`).
Контент рассчитывает на симметрию: `faction_traits.json:64-73` (`trait.propaganda_machine`,
`balanceBudget: 0`) парует `loyalty_add +2` со штрафом `research_cost_mult ×1.1` — сейчас штраф обнуляется,
трейт становится чистым бафом. Сделай кап `research` симметричным остальным каналам (production/upkeep/cost)
— подними/убери верхнюю границу так, чтобы `mult > 1` реально применялся.

### T1.4. `processTurn` не атомарен — сбой удваивает начисления при повторе

`processTurn.mjs`: `runEconomyTick` пишет `data/ledger.json` немедленно (`economyTick.mjs:1043`,
`writeLedger`), но номер хода фиксируется только в конце `processTurn` (`:1843-1849`, `writeLiveBoard`),
после `applyAllResearchQueues`, `applyAllBuildQueues`, `runLoyaltyPhase`, `resetAlchemyAttemptsForAll`.
`try/finally` (`:1703-1877`) сбрасывает только `tickFrozen`, не откатывает уже записанный гроссбух/приказы.
`backupTurnSnapshot(turn, "pre_tick")` (`:1658`) существует, но не восстанавливается автоматически при сбое.

Почини так: (а) инкремент/персист номера хода — **первым** шагом обработки, не последним, либо (б) если
порядок менять рискованно — на входе в `catch`-ветку `processTurn` restore из уже существующего
`pre_tick`-снапшота перед тем, как отдать ошибку наружу. Выбери (а), если не найдёшь скрытую причинно-
следственную связь, почему это сделано в конце (проверь git blame/комментарии); если найдёшь — сделай (б) и
задокументируй, почему.

### T1.5. `engagementReconcile.mjs` пишет мимо `tableStore`

`engagementReconcile.mjs:16-28` читает/пишет `data/engagements.json` через сырой `fs.readFileSync`/
`writeFileSync`, локально определённый, не импортированный из `tableStore.mjs`. `engagements.mjs:6,49,82`
читает/пишет тот же файл через `readJson`/`writeJson` из `tableStore.mjs`, которые идут через
`getStoreBackend()`. `cancelEngagementsMissingForces` вызывается из `tableStore.mjs:145` внутри **каждого**
`writeLiveBoard()`. Перепиши `engagementReconcile.mjs` на `readJson`/`writeJson` из `tableStore.mjs` — иначе
после C4 (переход этих данных на SQLite-бэкенд) правки отсюда перестанут быть видны остальному приложению.

### T1.6. Неатомарная запись + тихий фолбэк в файловом бэкенде

`db/storeAdapter.mjs`, `fileBackend().writeJson` (`:74-78`) — прямой `fs.writeFileSync` на боевой путь, без
temp-файла + rename. `readJson` (`:66-73`) — любая ошибка парсинга молча возвращает `fallback`.
`ledger.mjs:readLedger` (`:75-85`) — фолбэк на `{factions:{}, entries:[]}` при битом `ledger.json`. Примени
принцип №13/№14 из `PRINCIPLES.md`: temp+rename на запись, громкая ошибка на чтение (не менять поведение
вызывающего кода — просто перестать проглатывать ошибку молча, дать её наверх с понятным сообщением).

### T1.7. Тот же паттерн — для игрового контента

`contentLoader.mjs:62-70` (`readJsonSafe`) возвращает `{}` на ошибку парсинга для любого из ~50 файлов из
`FILE_KEYS` (`:11-58`). `gmBalance.mjs` (`applyGmBalancePatch`, функции вроде `setAp`/`setStartStock`/
`setForceMult`/`setAlchemy`, `~:161-262`) пишут `economy_balance.json`/`rules.json` неатомарно через
HTTP-запрос GM, затем горячо перезагружают контент. Почини по тому же принципу №13/№14: атомарная запись +
громкая ошибка при парсинге, чтобы битый файл не превращался в «весь каталог зданий тихо исчез из игры».

### T1.8. `faction_rebels` — легион без фракции

`loyalty.mjs:356` создаёт легионы восстания с `factionId: "faction_rebels"` — эта строка нигде больше не
встречается ни в одном файле контента, фракции не существует. Заведи минимальную запись-заглушку фракции
`faction_rebels` (нейтральная, без территории, без валюты — только чтобы `world.factions.find(...)` не
возвращал `undefined` для последующих проверок AP/upkeep/дипломатии) либо в `normalizeWorld.mjs` — автосоздание
такой записи при первом появлении легиона с этим `factionId`, если её ещё нет в состоянии мира.

### T1.9. Дробление флота даёт бесплатные очки действия

`apBudget.mjs:38-47` (`resolveForceApMax`) считает бюджет по числу флотов/легионов (`countFactionForces`,
`:27-33`), не по их размеру — дробление одного крупного флота на много мелких линейно увеличивает доступные
Force AP без платы.

**Решение зафиксировано заранее (не оставлять на усмотрение агента — иначе разные прогоны дадут разный
баланс):** убывающая отдача, не минимальный размер флота. Причина: минимальный размер флота требует решать,
что происходит с «недобитым» флотом ниже порога (авто-слияние? блокировка действий? штраф?) — лишняя
дизайнерская развилка, которую эта задача не должна открывать. Убывающая отдача решается одной формулой,
без побочных вопросов.

Реализация: `perFleet`/`perLegion`-бонус в `resolveForceApMax` должен убывать с порядковым номером
флота/легиона фракции (например: полный бонус для 1–3 флотов, половина бонуса для 4–6, четверть — дальше;
подбери конкретные пороги так, чтобы существующие балансные тесты/smoke не требовали пересчёта стартовых
кампаний — если есть эталонные значения AP в smoke-тестах, кривая обязана давать те же цифры для типичного
малого числа флотов, 1–3, и расходиться только при явном дроблении сверх этого). Задокументируй итоговую
кривую комментарием рядом с `resolveForceApMax`.
