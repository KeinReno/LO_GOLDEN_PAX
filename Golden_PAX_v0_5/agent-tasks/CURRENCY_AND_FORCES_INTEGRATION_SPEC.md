**Before touching anything**: read `Golden_PAX_v0_5/CLAUDE.md` in full — this project has hard rules (faction always explicit, ~400-600 line file cap, `server/domain/*` never touches DB/HTTP, content not code, tests before "done", `server/campaign/*Store.mjs` is the only DB boundary). Every existing domain file's header comment states plainly whether it's a byte-parity port of `../GMap/server/*.mjs`, a behavior-derived port, or new design not present in GMap at all — follow the same discipline for anything new: **when porting GMap behavior, verify by reading the actual GMap source, don't guess; when doing new design, say so explicitly in a header comment.**

Test discipline already established in this codebase, keep following it:
- If the GMap function you're porting is `export`ed and pure, write a **parity test** that imports both `../../../../GMap/server/X.mjs` and the new port and diffs outputs directly (see `server/domain/economy/flowEngine.parity.test.mjs` for the pattern).

## Priority 0 (do first, blocks everything else): a real metal/supply income floor

**The problem, confirmed by direct check of the shipped content**: zero buildings in `content/core/buildings.json` produce `currency.metal` or `currency.supply` via `yield_flat`/`production_flat`. After Stage 2 of the flow engine (`domain/planets/flowIncome.mjs`), the only currencies with any income at all are the 6 category currencies (extracta/materia/industria/energia/bios/cognitio) — `currency.metal`/`currency.supply` only ever get *spent* (building costs, unit costs, colonization costs, force costs) and never replenished. Every faction's metal/supply is currently a depleting resource with no floor — this is a live bug in the shipped economy, not a hypothetical.

**What GMap actually does** (`GMap/server/economyTick.mjs`, search for `mapResourceYieldLegacyOnly` and the `legacyGross` block around line 809-834): every faction gets a flat `{ "currency.metal": 0, "currency.supply": 2 }` baseline per tick, plus `mapResourceYieldLegacyOnly(sys, content)` per owned system — which sums `yield` from that system's **uncategorized** deposits (`map_resources.json` entries with `category == null` — these exist in the ported content, e.g. check for entries with no `category` field) plus `+1 currency.supply` if the system has any population. This whole thing is scaled by `logisticsProductionMult(sys, content)` (not ported here, not needed — skip it, it's a separate logistics-range system this project hasn't touched).

**What to actually build here** (simplified relative to GMap — this project doesn't have `system.resources` at all, only `planet.resources`, so a literal port isn't possible without inventing a whole system-level deposit concept first):

- New file `server/domain/economy/legacyIncome.mjs`. Header comment must say clearly: **not a full port** — GMap's version operates on system-level `sys.resources`, which this project never built (only `planet.resources` exists, see `domain/planets/extraction.mjs`'s — now deleted — history and `domain/planets/flowContribution.mjs`'s current header). This is a deliberately simplified stand-in: a flat per-faction supply baseline plus a small population-scaled add, capped low, same spirit as GMap's floor (keep the game playable without a peg) without inventing system-level deposits.
- Recommended shape (tune the constants, these are first-pass defaults like `laborSlots = tier` was — document them as such): `computeLegacyFloorIncome(ownedPlanetsCount, totalPopulation)` → `{ "currency.supply": 2 + Math.min(10, Math.ceil(totalPopulation * 0.05)), "currency.metal": 0 }`. Keep it capped and small — the whole point (see `notes/2026-08-13-currency-peg-grill.md`, Q4) is that this floor stays weak so committing to a currency peg (Priority 1) is a real strategic upgrade, not redundant.
- Wire into `server/campaign/turn.mjs` the same way `computeFactionFlowIncome`'s result is merged today — add this floor's output via the existing `mergeIncome` helper already in that file.
- Unit test with a small synthetic fixture (population scaling, cap behavior). No parity test possible here (this isn't a port).

## Priority 1: Currency pegs

**CORRECTION (added after this spec was first written and handed off — if you already started Priority 1 from the version below without reading this box first, stop and re-read before continuing):** GMap already has a real, working exchange system that implements most of the "peg strength" and "cross-faction rate" mechanics described below — it was missed in the original research pass. Read `GMap/server/fxExchange.mjs` (126 lines) and `GMap/server/marketRates.mjs` (104 lines) in full, plus `GMap/content/core/faction_currencies.json`, `GMap/content/core/faction_currency_bindings.json`, and `GMap/content/core/economy_schema.json`'s `fx_exchange`/`market` sections, **before** writing any peg-rate formula. Do not invent a new formula for peg strength or cross-faction rates — port `fxExchange.mjs`'s `instantPegCredit`/`refreshFxExchange` (EC = `reserveWeight·log1p(reserves) + extractionWeight·log1p(extraction)`, EMA-smoothed turn over turn, floored) and `marketRates.mjs`'s GM-override-wins merge — these are exported, mostly pure, real functions, not a stub (unlike the general `market` system in the same content, which GMap itself marks `"status": "stub"` — that stays out of scope, it's about arbitrary order-book trading, not pegs).

**What IS still new design on top of the ported GMap system** (GMap's fxExchange only computes *cross-faction reference rates* for GM-adjudicated trade — it never automatically converts a peg into a faction's own income): the asymmetric income mechanic from Q4 below (weak legacy floor without a peg, uncapped peg-conversion income *into that faction's own metal/supply*) is genuinely new — GMap has no equivalent. Build it as a layer that *consumes* the ported EC value (a faction's own currency's computed strength) as an input to how much metal/supply its peg-conversion produces per turn, rather than reinventing the strength formula.

GMap's content model is also more developed than the grill anticipated — reuse it as-is rather than inventing new content shape: `faction_currencies.json` already supports **multiple factions sharing one issued currency/peg** (`issuerFactionIds` — this already IS the "currency zone" from Q3/Q6, no need to build a separate "currency union" mechanic from scratch, joining a union is just adding a faction id to an existing currency's `issuerFactionIds`), and `faction_currency_bindings.json` already has real `treasuryPeg` + `seedStocks` per faction as a working example to follow.

Full design reasoning (why the asymmetry, why formula+bounded-GM-multiplier, why two independent relation tracks) already settled in `notes/2026-08-13-currency-peg-grill.md` — **read that file in full too**, it explains the decisions below, including one place the user directly overruled my first proposal (Q4) — don't re-litigate settled decisions, only the explicitly-flagged open ones below need a judgment call. Where that file's Q2/Q5 talk about "the formula" for exchange rate, treat that as now resolved by the ported `instantPegCredit`/EMA mechanism above, not a formula to invent.

### Settled design (do not deviate without checking with the user first)

1. **No new currency type.** A peg gives a real conversion path into the *existing* `currency.metal`/`currency.supply` — nothing new to add to `content/core/economy_balance.json`'s `start.stocks`.
2. **Asymmetry is the whole point** (Q4): Priority 0's legacy floor is deliberately weak/capped and available with no peg. Peg-conversion is **uncapped** and scales **non-linearly** with the faction's own extraction of the pegged resource relative to global extraction of that same resource — the rarer/more-dominant your peg globally, the stronger the multiplier (self-reinforcing, like a real reserve currency). If you build this as "just another income source with the same ceiling as the floor," you have built the wrong thing — the user explicitly rejected that shape.
3. **Exchange rate = formula baseline + bounded GM multiplier** (Q2/Q5): automatic formula from relative global extraction dominance, with the GM able to apply a bounded multiplier on top (recommended range 0.8x-1.5x, confirm with user if you want a different band) for narrative events. Not a free-form manual override of the whole rate.
4. **Peg-to-peg exchange, three coexisting mechanisms** (Q3): (a) direct barter of raw strategic resources, no conversion needed, always available; (b) a formal bilateral exchange-rate deal between two specific factions; (c) full currency-union/absorption (one faction adopts another's peg).
5. **(b) and (c) are NEW, dedicated economic relation types** (Q6), **on an independent track from political relations** (Q7) — a faction pair can be simultaneously e.g. allied (political) and in a currency union (economic). This requires changing `server/domain/diplomacy/treaties.mjs`'s `syncTreatiesFromEdge`, which currently replaces *any* existing relation with the new one (`d.treaties = treaties.filter(t => t.withFactionId !== other.id)` before adding). Add a `track` field to every entry in `content/core/diplomacy_stances.json` (e.g. `"political"` for the 10 existing ones, `"economic"` for the 2 new ones), and change the filter to `t.withFactionId !== other.id || t.track !== newTrack` (or equivalent) so same-track relations replace each other but different-track relations coexist. Check `server/domain/diplomacy/treaties.parity.test.mjs`/`treaties.test.mjs` still pass, and add a new test proving political+economic coexist.
6. **Peg can change later, but with a transition penalty** (Q8): not instant/free. Recommended shape (not fully specified in the grill, use judgment): new peg's conversion multiplier starts reduced (e.g. 0.5x) for N turns (recommend N=5, both numbers are first-pass defaults to document as such) after a peg change, ramping back to full strength linearly. Store `pegChangedTurn` per faction to compute this.

### Open implementation decisions (not resolved in the grill — use the recommended default, but flag clearly in your PR/commit message so it can be revisited)

- **Does the pegged resource's extraction still ALSO count toward its normal category income, or does pegging redirect it away from the category and only into peg-conversion?** Recommended: **additive, not a redirect** — the resource keeps contributing to its category normally (via `domain/planets/flowContribution.mjs`, unchanged), and peg-conversion taps the *same turn's extraction rate of that specific resource* as a separate, additional calculation. This is the least disruptive to what's already shipped and tested. Do not build a "redirect" mechanic without checking with the user — it would require tracking per-resource (not just per-category) rate through the flow grid, a bigger change.
- **Exact non-linear formula for peg strength.** Recommended first pass: `rate = baseRate * (globalTotalExtractionOfThatPeg / thisFactionsExtractionOfThatPeg)` clamped to a sane floor/ceiling (e.g. `[0.5, 5.0]`) so it can't divide-by-near-zero into an absurd number — document this clamp explicitly as a first-pass safety default. "Global" here means summed across every faction currently extracting that specific strategic resource in the campaign (you'll need a small helper that sums peg-resource extraction across all factions' planets — reuse `domain/planets/flowContribution.mjs`'s per-planet category-staffing logic to find how much of the pegged resource id each planet's deposits contribute).
- **GM multiplier scope**: per-peg-resource (affects every faction using that peg) or per-faction (affects one faction's peg specifically even if others share it)? Recommended: **per-peg-resource** — simpler data model (one multiplier per strategic resource id per campaign, not per faction), and thematically matches "confidence in a currency" being a property of the currency itself, not of one holder.

### Suggested file layout

- `server/db/schema.sql`: add `peg_resource_id TEXT` and `peg_changed_turn INTEGER` (nullable) to the `factions` table. Add a small table or column for GM-set per-peg multipliers (e.g. `peg_rate_overrides(campaign_id, resource_id, multiplier)`).
- `server/domain/economy/currencyPeg.mjs` (new): pure functions — `strategicResourceIds(content)` (reads `content.economy_schema.resource_ranks.strategic`, already real content, already used by GMap's `strategicResourceIdSet` — check `GMap/server/flowEngine.mjs` for the exact shape if you want a parity-testable helper), `computePegRate(pegResourceId, extractionByFactionByPeg, gmMultiplier)`, `convertPegExtractionToTreasury(extractionAmount, rate)`, `pegTransitionMultiplier(pegChangedTurn, currentTurn)`.
- `server/campaign/campaignStore.mjs`: extend `addFaction`/`getFaction`/`listFactions` to read/write `pegResourceId`/`pegChangedTurn`; add a `setFactionPeg(db, campaignId, factionId, resourceId, turn)` function.
- `content/core/diplomacy_stances.json`: add `track` field to all entries; add the 2 new economic relation types.
- `server/domain/diplomacy/treaties.mjs`: track-aware replacement (see point 5 above).
- `server/campaign/turn.mjs`: wire peg conversion income into the economy step alongside Priority 0's floor and Stage 2's flow income.
- New API routes (`server/api/routes/` — probably a new `currency.mjs` route file, plus contract schemas in `server/api/contract/currency.mjs`): GM sets a faction's peg (`POST /campaign/:id/factions/:factionId/peg`), GM sets a rate-multiplier override, factions propose/accept an exchange deal or currency union (extends the existing `POST /campaign/:id/relations` pattern in `server/api/routes/campaign.mjs` — read that route first, follow its actor/auth pattern with `requireGm`/`requireActor`/`actorCanActForFaction`).
- Tests: unit tests for `currencyPeg.mjs`'s pure functions (no GMap equivalent exists — this is new design, say so), a `treaties.test.mjs` addition proving the two-track model, and a live verification script proving: faction picks a peg, extracts the pegged resource, gets real metal/supply income beyond what the Priority 0 floor alone would give.

## Priority 2: wire raised forces into combat

Right now `domain/forces/recruitment.mjs`'s `raiseUnit` produces a combat-shaped composition `group` (`defId`/`tier`/`roles`/`count`/stat fields/`maxHp` — see its return value), persisted via `server/campaign/forcesStore.mjs`, but **nothing calls `domain/combat/resolveExchange.mjs` with it**. `resolveExchange` is still stateless-preview only (`server/api/routes/combat.mjs`), same as it's been since the domain was first ported — see `server/domain/forces/README.md`'s "Not attempted this pass" list.

### What to build

- New route, likely `POST /campaign/:campaignId/forces/:forceAId/engage` (body: `{ forceBId, stanceA, stanceB }`, or similar — look at `server/api/contract/combat.mjs`'s existing `ResolveExchangeRequestSchema` for the exact shape `resolveExchange` needs and mirror it) in a new or extended route file. Loads both forces via `forcesStore.mjs`'s `loadForce`, checks the caller's actor can act for `forceA`'s faction (same `requireActor`/`actorCanActForFaction` pattern as everywhere else — `forceB` doesn't need to belong to the caller, mirrors how `combat.mjs`'s existing preview route already treats `groupsA`/`groupsB` as just data), calls `resolveExchange(forceA.composition, forceB.composition, stanceA, stanceB, forceA.factionId, forceB.factionId, content)` (check the exact signature in `server/domain/combat/resolveExchange.mjs` — don't guess, read it).
- After combat: `resolveExchange`'s result already has `groupsA`/`groupsB` post-casualties, already pruned of destroyed (count:0) stacks via `removeDestroyedGroups` (see `domain/combat/casualties.mjs`'s header for why that pruning exists — a real bug this project already found and fixed once, don't reintroduce it). Persist: if the resulting composition is non-empty, `saveForce` with the updated composition; if it's now empty (`[]`), `deleteForce` (matching the exact pattern `server/api/routes/forces.mjs`'s disband route already uses for a fully-destroyed force).
- Response should include the full `resolveExchange` result (outcome, powerA/powerB, updated compositions) plus which force(s) got deleted, if any.

### Known, pre-existing, out-of-scope gap — do not try to fix this here

Ground units (`unit.*`/`ground_unit.*` from `content/core/units.json`) use stat fields `defense`/`speed`; `domain/combat/roleMatchups.mjs`'s power formula reads `damage`/`accuracy`/`shields` (ships' stat shape). A raised legion's `group` object will carry whatever stats its content def actually has — for ground units that means `accuracy`/`shields`/`armor` are simply absent, and the combat formula treats missing fields as 0, which degenerates that side's power calculation. **This is a content-shape mismatch that predates this spec** (see `server/domain/forces/README.md`'s explicit note on it) — ships will combat correctly through this new integration, ground units will combat but with degenerate power numbers. Do not invent a stat-mapping formula to "fix" this without checking with the user first — it's a real design question (how should ground combat power actually be computed?), not an implementation detail.

### Tests

- Behavior test for the new route's persistence logic (force deleted on wipeout, saved with pruned composition otherwise) — can reuse `server/domain/combat/resolveExchange.test.mjs`'s existing fixtures for the actual combat math, that domain function doesn't change.
- Live verification: raise two forces (or one raised + one hand-typed as in `scripts/playtestCampaign.mjs`), engage them, confirm the loser's force is actually gone from a subsequent `GET .../factions/:id/forces` call if wiped, and that population isn't magically returned (a combat loss is not a disband — no population should flow back to any planet from combat, only from the existing `POST .../forces/:id/disband` route).

**File-overlap warning**: both sub-sections touch `server/domain/planets/*` (`construction.mjs`, `flowContribution.mjs`, `flowIncome.mjs`) and `server/db/schema.sql`'s `planets`/`systems` tables — the same files Priority 3c (procedural deposit generation) and the flow-engine work already touch. ### 4a. Planet slot-grade progression

**Context**: `surface_slots`/`orbital_slots` are already real columns (`server/db/schema.sql`, defaults 8/4), read by `construction.mjs`'s `canPlaceBuilding` slot-capacity gate. They're currently static — set once at planet creation, never changed after. The galaxy-migration grill found that old GMap capitals had absurd, unearned slot counts (118/24 — confirmed via grep that no tech/building/formula anywhere in GMap ever touches these fields, they're static hand-placed data) and decided this project needs a real, earned progression instead of either keeping those numbers or picking a bigger static default.

**What to build**:
- `grade` column on `planets` (`INTEGER NOT NULL DEFAULT 1`, range 1-5) plus a separate `orbital_grade` column (independent counter — surface and orbital grow on separate scales, per the settled design). Wire into `planetStore.mjs` (`PLANET_COLUMNS`, `createPlanet`, `rowToPlanet`, `savePlanet`) the same way `resources_json` was added there.
- `surfaceSlots` becomes derived from `grade`, not a free-standing number: grade 1→8 (today's default), grade 5→48. Steps in between at your discretion (recommend evenly spaced: 8/18/28/38/48, document as first-pass). `orbitalSlots` derived from `orbital_grade` on a smaller separate range (recommend 4→12, e.g. 4/6/8/10/12).
- New domain module `server/domain/planets/planetGrade.mjs`: `surfaceSlotsForGrade(grade)`, `orbitalSlotsForGrade(orbitalGrade)`, `gradeUpgradeCost(currentGrade, content)` (new `economy_balance.json` entry, e.g. `planetGrade.upgradeCost` — an array of costs per step, scaling up; exact numbers are your call, document as first-pass), `upgradeSurfaceGrade(planet, stocks, content)` / `upgradeOrbitalGrade(planet, stocks, content)` — same shape as `construction.mjs`'s `placeBuilding` (afford-check via `canAffordCost`, spend via `adjustStock`, return `{ ok, planet, stocks, journal }` or an error). NOT a port — say so in the header.
- Update `construction.mjs`'s `canPlaceBuilding` slot check to derive the cap from grade (`surfaceSlotsForGrade(planet.grade)`/`orbitalSlotsForGrade(planet.orbitalGrade)`) rather than reading the raw stored field directly — or keep the stored field in sync as a denormalized convenience column if that's simpler; either way the derivation function is the source of truth.
- New route (`server/api/routes/planets.mjs` if that file exists, else extend wherever planet actions live in `campaign.mjs`'s routes): `POST .../planets/:id/upgrade-grade` (body: `{ zone: "surface" | "orbital" }`), same actor/auth pattern as every other persisted action (`requireActor`/`actorCanActForFaction`).
- Migrated planets' starting grade (`grade = min(5, smallest grade whose surfaceSlots >= migrated building count)`) is the separate migration script's job, not this priority's deliverable — just don't shape `surfaceSlotsForGrade` in a way that makes that later lookup awkward (easy to invert/search).

**Tests**: unit tests for the slot curves and upgrade-cost function (new design, say so), a `construction.test.mjs` addition proving building placement respects grade-derived slots, live verification of the new route.

### 4b. Space objects: economy + combat effects, with depletion

**Context**: GMap's `spaceObjects` (system-level tags like `asteroid`, `pirate`, `wormhole`) is a real content-driven mechanic, not flavor data — `GMap/content/core/space_objects.json` defines 19 types with `capacity_add`/`rate_mod`/`demand_mod` effects on flow category/tier, applied automatically to whoever owns the system via `GMap/server/flowEngine.mjs`'s `applySpaceObjectEffects` (~line 464, called from `economyTick.mjs`'s per-system loop). This project builds a richer version: contestable via combat (not auto-granted), effects reach into combat too (not just economy), and resource-flavored objects deplete from use. Read `GMap/content/core/space_objects.json` and `applySpaceObjectEffects` before starting — the economic-effect shape ports directly, the rest is new.

**Settled design** (don't deviate without checking with the user first):
1. **Control = system ownership, no new mechanic.** Whoever holds `system.ownerFactionId` controls every space object in that system and receives its effects. Taking the system (via `domain/combat/resolveExchange`) IS contesting its objects — there is no separate "presence"/claim concept to build.
2. **Effect domains this pass: economy + combat only.** Loyalty and diplomacy effect types stay reserved in the content schema (already designed to be extensible per its own `extensibility` block) but get no implementation — neither domain has a system-location concept to hook into yet.
3. **Depletion is usage-based, for resource-type objects only, and is genuinely new — do not treat it as reusing an existing pattern.** `asteroid`/`comet`/`debris` (the types whose effect is a `rate_mod`, i.e. something actively drawn from) lose a real remaining-amount as they're extracted from over turns. **Important, checked directly in this codebase**: planet deposits (`planet.resources`, `domain/planets/flowContribution.mjs`'s `addExtraction`) currently never deplete — they're an infinite income source, already shipped and tested that way. Space-object depletion has no precedent to copy here; design it from scratch. Planet deposits are explicitly OUT of scope for this priority — do not add depletion to them, the user confirmed this stays space-objects-only.
4. Astronomical/anomaly types (`black_hole`/`wormhole`/`nebula`/`pulsar`/`storm`/`grav_field`/`anomaly`/`ruin`/`dead_zone`/`hub`/`relay`/`forge`/`science_arch`/`leviathan`) are permanent — no depletion — unless destroyed as a combat side effect or by GM action.

**What to build**:
- `content/core/space_objects.json`: port GMap's file (19 types, same `effects` shape). Decide how "depletes" is determined per type — GMap's existing `kind` field already roughly distinguishes resource types (`asteroid`/`comet`/`debris` are `kind: "field"`, but so are `nebula`/`dead_zone`/`storm`, which don't deplete per point 3-4 above) — `kind` alone isn't a clean enough signal, so add an explicit `depletes: true` flag to the resource-type entries rather than inferring it.
- Schema: `systems` need per-instance space-object state (not just a static tag list like GMap's flat `spaceObjects: string[]`) so depleting types can track a remaining amount. Recommend a real typed table, `system_space_objects (id, system_id, type_id, remaining_amount NULL for non-depleting types)`, per CLAUDE.md rule 5 (no blob/kv shortcuts) — a `space_objects_json` column on `systems` is defensible only if remaining-amount tracking turns out trivially simple; document whichever you pick and why.
- New domain module — `server/domain/planets/spaceObjects.mjs` unless a systems-specific domain folder already makes more sense (check first): `spaceObjectEffects(system, content)` → economic effects for the flow grid (same shape as GMap's `applySpaceObjectEffects`, adapted to this project's `flowEngine.mjs`), `spaceObjectCombatModifier(system, content, side)` → a bonus/penalty for `resolveExchange`, `depleteSpaceObject(system, typeId, amountExtracted)` → updated remaining-amount, removing the object once it hits zero.
- Wire the economic effect into `flowContribution.mjs`/`flowIncome.mjs`'s existing 3-pass structure — **read that file's header comment on the pass-ordering bug before touching it** (extraction + ambient baselines must exist across every planet/system before any converter runs — the same discipline applies here; verify the right pass by comparing against GMap's real per-system loop order in `economyTick.mjs`, don't guess).
- Wire the combat modifier into wherever Priority 2's new `.../forces/:id/engage` route calls `resolveExchange` — pass the system's space-object combat modifier alongside `groupsA`/`groupsB`. If Priority 2 hasn't shipped yet when you reach this, coordinate on the route's actual shape rather than guessing.
- Depletion: after each turn's extraction (in `turn.mjs`'s economy step, alongside where `flowIncome`/Priority 0/Priority 1 already run), call `depleteSpaceObject` for every resource-type object actually drawn from that turn, using the same amount added to the flow grid.

**Open implementation decisions** (recommended defaults, flag clearly for revisit — no grill guidance on exact numbers):
- Starting `remaining_amount` and depletion rate for resource-type objects — pick something that lasts a meaningful number of turns (recommend 50-100 turns of average extraction).
- Combat modifier magnitude per type (e.g. does `minefield` reduce attacker power by 10%? 20%?) — use small values (5-15% range), consistent with how other first-pass balance numbers in this project are documented.
