# domain/planets

Systems, planets, colonization, building placement — the "world" model every other domain's README has been pointing at as the missing piece. Ported from `GMap/server/planetActions.mjs` (+ `biomeMatch.mjs`, `buildingAccess.mjs`), validated against `content/core/buildings.json`, `colonies.json`.

**Why this exists now**: a real 10-turn playtest (`scripts/playtestCampaign.mjs`) made it obvious that without this, "playing the game" was just a human typing plausible-looking income numbers into `categoryIncome` every turn — economy/combat had real formulas but nothing underneath actually producing the inputs. This domain is step one of closing that gap: real planets, real buildings, real (partial) income from them.

**Inputs/outputs**: plain data in (a system + planet + building def + faction), plain data out (updated planet/stocks/journal). No DB/HTTP here — `server/campaign/planetStore.mjs` persists it, `server/api/routes/planets.mjs` exposes it.

**Multiplayer**: colonization and building placement always take `factionId` explicitly and check real ownership (`canColonizePlanet`, `canFactionBuildDef`) — nothing here assumes a single owner per system.

## Status: real rules for a meaningful subset, honestly bounded

Byte-parity tested against GMap (exported and pure there, or verified against real content):

- `biomeMatch.mjs`, `buildingAccess.mjs` — fully parity-tested, exported+pure in GMap
- `populationCap.mjs`'s `planetCapFromBuildings` — parity-tested **against real `content/core/buildings.json`+`colonies.json`**, not synthetic data. This is the real `cap` input `domain/economy`'s population growth curve needs — no longer a caller-invented number for any faction whose planets are tracked here.

Behavior-tested (module-private or reshaped in GMap, re-derived from source): `colonization.mjs`'s `canColonizePlanet`/`colonizePlanet`, `construction.mjs`'s `canPlaceBuilding`/`placeBuilding` (real slot-capacity, `maxPerPlanet`/`maxPerSystem`, biome, and faction/race-access rules — the actual placement logic from GMap's `applyPlanetAction`, minus AP gating and intent recording, since this project hasn't ported GMap's AP-budget system).

**`colonizePlanet`'s population/race handling (`raceComposition.mjs`) is not a port — new design from `notes/2026-08-12-population-race-forces-grill.md`.** GMap only ever handed out a flat `colonizePopulation` number with no race breakdown and no source. Here, colonization has two modes (`opts.mode`): **auto** keeps GMap's flat quantity-by-colony-type but rolls the race mix (1d6 purity roll — pure/light-mix/heavy-mix, secondary races weighted from the faction's own existing population); **manual** takes the caller's exact per-race settler counts. Either way, population sent is a **real transfer** — it's deducted from the faction's other planets (proportionally across every planet with that race, or from one explicit `opts.sourcePlanetId` in manual mode) via `deductRaceAcrossPlanets`/`withDeductedRacePopulation`. A faction's very first colony (no owned planets yet) is exempt from deduction — there's nothing to transfer from yet, same as GMap's original behavior for a founding world.

**A subsurface/deep zone-slots gap flagged during that grill session turned out to be a false alarm** — GMap deliberately shares one `surfaceSlots` pool across `surface`/`subsurface`/`deep` zones (`GMap/server/planetActions.mjs:418-425`, zone kept only as a label on the building instance), and `construction.mjs` already replicates this correctly. Don't add separate `subsurfaceSlots`/`deepSlots` fields — that would be a deviation from GMap, not a fix.

**`laborAllocation.mjs` is not a port — new design from `notes/2026-08-12-population-race-forces-grill.md`.** `content/core/buildings.json` gained a `laborSlots` field on every building (currently `= tier`, a first-pass balance default written by a one-off script, not hand-tuned — GMap has no equivalent field at all). `allocateLabor` spends a planet's population across its buildings in placement order until it runs out; `flowContribution.mjs` scales every building's output (and each category's deposit extraction) by its staffed fraction. This is what makes an under-populated colony's buildings genuinely compete for workers (verified live: econos's `materia.smelter`, built after `building.mine` already claimed the planet's whole population, converts nothing until more population arrives). `pop_cap_add` (housing) is deliberately NOT labor-gated — see the file's header for why.

**`flowContribution.mjs` + `flowIncome.mjs` are Stage 2 of porting GMap's flow engine** (superseding the old `buildingYields.mjs`/`extraction.mjs` from Stage 1, both deleted — Stage 1 computed currency directly per building/deposit, which couldn't coexist with real RPS conversion where one building's output is another's input). The 6-category flow matrix itself (`domain/economy/flowEngine.mjs`: categories, RPS edges, the bottleneck rule, `computeNets`/`categoryTotals`/`bottlenecks`) is byte-parity tested against GMap — exported+pure there. `flowContribution.mjs`'s per-planet feeders (deposit extraction, building yield/convert, upkeep-slot demand) are ported behavior with two explicit, already-agreed deviations (`notes/2026-08-13-resource-extraction-grill.md`): (1) a deposit only extracts behind a matching-`category` building — GMap extracts for free, but that breaks the "nothing is free" principle from the population/forces grill; (2) every contribution is scaled by real per-planet `allocateLabor` job-slots, not GMap's `biosLaborScale` (a faction-wide currency.bios-stock proxy) — one unified labor model across the whole economy. Verified live: a `map.iron` deposit yielded nothing until `building.mine` was built, then contributed real `currency.extracta` alongside the building's own `yield_flat`, correctly summed by the shared grid.

**Explicitly NOT in Stage 2** (deliberate, matches project-wide accepted gaps, not oversights — see `flowEngine.mjs`'s header): GMap's "legacy metal/supply bridge" (a double-count guard that doesn't apply the same way here since Stage 1 already diverged the currency landscape). Strategic-resource dual-tracking is now Pass 5 of `flowIncome.mjs` (`CURRENCY_PEG_SPEC`): raw `map.*` stock credit plus dominance-rate metal/supply for a treasury peg.

**`depositGeneration.mjs` is not a port — new design from `notes/2026-08-13-resource-extraction-grill.md` Q1.** Optional `autoGenerateResources` on `POST .../planets` rolls 1–3 (first-pass default) deposits whose `biome_tags` match the planet via `biomeMatch.mjs`. Empty `biome_tags` are skipped. Explicit `resources: string[]` (including `[]`) still wins — GM-authored deposits remain fully supported.

**`planetGrade.mjs` is not a port — new design from `notes/2026-08-13-galaxy-migration-grill.md` Q3.** `surfaceSlots` grows 8→48 over 5 grades; `orbitalSlots` grows 4→12 on a separate counter. Both advance via `POST .../planets/:id/upgrade-grade` (currency cost from `economy_balance.planetGrade`, instant like `placeBuilding`). Grade is the source of truth; stored slot columns are denormalized. Migrated planets' starting grade is `scripts/migrateGalaxy.mjs` / `domain/planets/galaxyMigration.mjs` (smallest grade that fits the kept building count).

**`spaceObjects.mjs`:** `applySpaceObjectEffects` is a byte-parity port of GMap's exported function. Control, combat modifiers, and depletion are **not** a port (grill Q4/4a/4b/4c/4d). Control = `system.ownerFactionId` (no presence mechanic). Economy + combat effects this pass; loyalty/diplomacy reserved. Resource types (`depletes: true` — asteroid/comet/debris) lose `remainingAmount` each turn equal to the rate they added to the flow grid. Planet deposits stay infinite — depletion is designed from scratch, not copied from `addExtraction`.

**Not attempted this pass**: racial building variants (`GMap/server/variantResolver.mjs`), demolish/`set_colony_type` actions, system generation/presets (`content/core/system_presets.json` isn't consumed anywhere yet — systems/planets are created via plain data through the persisted API, not procedurally).

Tech-gated building access (`canBuildWithTech`) **wired 2026-08-14** — `construction.mjs`'s `canPlaceBuilding`/`placeBuilding` now take an optional `techAccount` and enforce `domain/tech/techGate.mjs`'s tier cap. Found live: nothing had ever read `techTiers` before this, meaning tier-10 buildings were placeable turn 1 with zero research — see `notes/2026-08-14-tech-tree-audit.md`.
